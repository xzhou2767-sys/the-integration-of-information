# 全体系文档同步（project-system-sync）

`docs/PROJECT_SYSTEM.md` 是本项目唯一全体系工程文档。**任何产生实质变更的任务收尾时，必须同步更新它**，
使其始终可被新接入的 agent 直接当作项目现状的权威来源。

## 一、触发判据

任务满足以下任一条即需更新（仅在**确无变更**时跳过，如纯咨询、只读排查未得结论）：

- 新增/修改/删除了任何 `.kt`、`.py`、`.kts` 文件
- 依赖版本、Gradle 模块、构建产物形态变化
- 新增或调整 REST 端点、DTO 字段
- 新增持久化文件或存储键
- 平台增删、类目体系调整
- AI 模型链、档位分级、成本模型调整
- 部署/发布流程、版本号变化
- 产出新的平台限制、技术结论、踩坑教训

## 二、更新流程

1. 读 `docs/PROJECT_SYSTEM.md` 全文（不要凭记忆改）
2. 对照下方映射表定位**受影响章节**（通常 1–3 节）
3. 只改受影响部分——**保留既有结构、编号与未受影响内容**
4. 更新文首「版本基准」（客户端 versionCode/versionName）与「最后更新」日期
5. 自检：编号连续、表格管道符成对、路径/接口/版本号精确（禁止"大约""可能"）、新结论附实测证据
6. 若新增了文档或 skill，补进「附录：文档索引」

## 四、写作原则

- **单一事实源**：文档只描述现状与已确认结论，不写猜测；未验证的写在「待评估」并标注未验证
- **精确优先**：接口路径、字段名、枚举值、版本号、文件路径必须逐字符准确
- **成本透明**：涉及 AI/抓取的成本相关改动，同步更新对应档位表与预算说明
- **教训沉淀**：踩坑类结论写入 11.3，注明触发条件与应对方式，避免后续 agent 重复试错
- **克制扩节**：优先并入既有章节；仅当出现全新领域（如新增大类能力）才新增一级/二级节

## 五、与其他技能的边界

- 部署/出包/验证命令 → `trae-server-deploy`（本文档只记录流程摘要，不重复命令细节）
- 平台增删的完整对齐清单 → `platform-onboarding`（本文档只记录结论性现状）
- 本技能**只负责文档同步**，不执行代码修改、部署或测试
